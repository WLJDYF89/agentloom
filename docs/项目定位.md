# 项目定位

> 这份文档回答一个问题：**agentloom 到底是个什么东西，以及在不同场合该怎么称呼它。**
>
> 它不描述技术方案（那是 `docs/events.md` 和代码的事），只锁定「对外怎么说」。
> 写于 A01 之后、A02 之前。后面 A40 写 README、A41 写讲稿时，直接从这里取材。

---

## 一、一句话定位

**agentloom 是一个可恢复的 Agent 执行内核。**

它回答的问题只有一个：

> 这个 Agent 能不能安全跑完一件多步任务，中途挂了能不能接着跑，副作用会不会重复。

注意这句话里没有「系统」「平台」「中台」任何一个词。这是故意的，原因见第五节。

---

## 二、它是什么，不是什么

| 参照物 | 是不是 | 依据 |
| --- | --- | --- |
| 一个 App（如客服机器人） | **不是** | 没有用户体系、没有业务流程、不产生业务数据 |
| 一个框架（如 LangGraph） | **不是** | 框架是给人搭 App 用的，它反而是被搭进 App 里的那一层 |
| 一个通用工作流引擎（如 Temporal） | **不是** | 见第四节 |
| PostgreSQL 的 WAL + 事务隔离 | **最接近** | 业务代码从不直接调用 WAL，但没有 WAL 就没人敢断言 commit 成功 |

这个 WAL 类比不是修辞。它精确地表达了定位：

- **WAL 服务的是「写操作能不能被证明成功」**，本项目服务的是「工具调用能不能被证明只发生过一次」。
- 两者都是**横切能力**：不产生业务价值，但所有产生业务价值的东西都依赖它。
- 两者都是**没人想自己写、但人人都需要**的东西。

所以准确的自我描述是：**它是一层基础设施组件，形态上是库，形态之外还带一个可视化控制台。**

## 三、业务载体：工单台 + 通知

说「不做业务」不准确。排期表 A18 规定了六个内置工具：

| 工具 | 有无副作用 | 用途 |
| --- | --- | --- |
| 查工单 | 无 | 只读，用于演示无副作用路径 |
| 建工单 | **有** | 幂等与两阶段标记的主要演示对象 |
| 发邮件（模拟） | **有** | 配合 A22 越权拦截（只允许内网域） |
| 查日志 | 无 | 只读，演示结果截断与结构化 |
| 只读 SQL | 无 | 演示参数校验与危险 SQL 拦截 |
| 发通知 | 无 | 演示多工具串联 |

所以场景是**企业内部工单台 + 通知**。但要分清主次：

> **业务是载体，不是目的。** 六个工具存在的唯一理由是「有东西可调用、可产生副作用、可被拦截」。
> 全部换成电商下单或文件批处理，内核一行不用改。

这个区分在面试里必须主动讲，否则会被当成「做了个工单管理系统，但功能不全」。

## 四、怎么回答「这不就是把 LangGraph / Temporal 重写了一遍」

**这是本项目最大的风险问题，必须提前背熟。** 答不好，项目就从「有深度」掉到「重造轮子」。

### 4.1 Temporal 不同在哪

Temporal 是**通用**工作流引擎，它不知道 Agent 语义：

- 不知道什么是「工具调用」，工具只是一次 activity
- 不知道什么是「人工审批」，approval 只是一次 signal
- 不知道什么是「上下文裁剪」「token 预算」
- 用它做 Agent，必须在外面再套一层 Agent 语义层——那一层正是本项目的主体

### 4.2 LangGraph 不同在哪

LangGraph 的 checkpoint 机制是**序列化整个 state**：

- **状态结构一变，历史 checkpoint 全部失效**（没有事件溯源，没有「从事件流重建任意时刻状态」的能力）
- **它不解决副作用去重**。工具执行到一半崩了，恢复后要不要重跑那个工具？LangGraph 把这个问题留给业务侧。

本项目对这两点都有明确答案：

- 事件流是**不可变日志**，schema 演进时老事件仍能重放（事件带 version 字段，A03 定）
- 副作用去重是**内核职责**，不是业务职责（A19–A21）

### 4.3 一句话版答案（面试用）

> **LangGraph 提供的是「编排」——下一步该干什么；本项目提供的是「正确性」——干完之后能不能被证明干过、且只干了一次。**
>
> 这两件事在数据库里对应「查询优化器」和「事务管理器」，是两套完全不同的知识，不存在谁取代谁。

### 4.4 差异化护城河（真正要讲透的三步）

排期表 A21 备注原文：**「本项目最硬的一处，也是面试最值得讲的一段」**。

| 步骤 | 任务 | 解决什么 | 一句话讲法 |
| --- | --- | --- | --- |
| 1 | A19 幂等键 | 同一次调用的身份 | `hash(run_id + step_seq + tool_name + normalized_args)`，参数归一化是前提 |
| 2 | A20 两阶段标记 | 执行中崩溃留痕 | 先写「执行中」，执行，再改「已完成」；写标记与执行业务必须可区分 |
| 3 | A21 三态判定 | 崩溃后怎么恢复 | 重启扫「执行中」记录，判定「未执行 / 执行中 / 已执行」，走不同路径 |

**这三步讲不透，整个项目就会被归为「重写轮子」。** 这是唯一一条不可妥协的讲解主线。

## 五、措辞规矩：对外用「系统」，对内用「内核」

### 5.1 为什么需要两套词

两个受众，两种信息需求：

| 受众 | 关心什么 | 该用什么词 | 为什么 |
| --- | --- | --- | --- |
| HR / 猎头 / 简历初筛 | 这是个什么类别的东西 | **系统 / 控制台** | 「内核」他们无法归档；「系统」能立刻定位到「AI 应用」 |
| 技术面试官 | 你解决了什么难问题 | **内核 / 库** | 「系统」会触发「那你用户体系呢」的追问，反而失分 |

### 5.2 具体怎么用

**简历上（面向初筛）**：

```
agentloom — 可恢复的 Agent 任务执行系统（执行内核 + 实时控制台）
```

或者更省事的版本：

```
Agent 执行内核与实时控制台
```

关键是**必须出现「控制台」或「界面」这类词**，让对方能想象出一个能看的东西。纯后端库在初筛阶段是有损耗的，这是事实，不必硬扛。

**README / 技术文档里（面向工程师）**：

统一写**内核**。开头第一段就把范围主动缩小：

> 这是一个内核，它只做一件事：保证一次工具调用有且仅有一次副作用。

**不要写**的自我限定：「我们没有用户体系」「我们没做权限管理」——这些话在 README 里向工程师交底可以（作为范围声明），但不要出现在简历上。

### 5.3 一条铁律：主动缩小范围，然后在自己划定的范围内无可挑剔

如果 README 写「我们构建了一个 Agent 执行系统」，面试官立刻去找系统该有的东西——用户、权限、部署形态、运维——一个都找不到，信任瞬间崩塌。

反过来，开头就说「我只做这一件事」，然后通篇用数字证明这件事做到了，可信度反而极高。

这与排期表要求 README 主动写「为什么不用微服务」是同一个逻辑：**先自己把质疑说出来，别等着被问。**

## 六、它是完整产品，不是半成品

### 6.1 半成品的定义

「半成品」不由「是不是系统」定义，而由**链路是否闭合**定义。

这个项目最终形态**并不是纯后端库**。排期表 P8 五个任务、32 小时、占全项目 15% 工时，产出的是：

- run 列表 + 新建任务 + 详情路由 + 连接状态指示器（连上 / 重连中 / 断开）
- 事件流时间线：逐条追加、虚拟滚动、按类型着色、点开看 payload
- 审批卡片 + 断点恢复按钮（审批后重拉快照，不在前端本地改状态）

这已经是一个能看到东西的完整界面：打开浏览器 → 新建任务 → 看它一步步执行 → 在工具调用前点「同意」→ 杀掉进程 → 点「恢复」→ 看它接着跑到终点。

**有界面、有交互、有状态、能演示——形态上它就是系统。**

### 6.2 两种「完整」的差别

| | 横向完整（业务系统） | 纵向完整（本项目） |
| --- | --- | --- |
| 靠什么证明 | 功能列表：我做了 A、B、C、D | 指标数字：在 X 条件下达到 Y |
| 弱点 | 每一项都能被追问「这个有什么用」 | 只有一条主线，但每一层都能深挖 |
| 容易被质疑 | 「这些功能是模板生成出来的吧」 | 「这个数字怎么测的」← 你能答 20 分钟 |

**真正的风险点不在命名策略，而在砍任务时的直觉。** 时间紧时人会砍「测试和文档」保「功能」——对这个项目是致命的，因为它的全部价值在「可验证」三个字上。所以排期表把 A37、A38、A39、A40 全标成 P0 不是偶然。

### 6.3 收口标准（A40 原文）

> **面试官只看 README 能问出 3 个问题。**

注意：标准不是「README 要显得很厉害」，是「**能问出 3 个问题**」。能让人追问 = 有内容；让人问不出话 = 真的单薄。

## 七、数字表（简历与 README 共用，实测后填）

**铁律：编的数字一问就露。以下数字必须在 P9 跑出真实结果后才允许写进去。**

| 指标 | 口径 | 目标 | 实测 | 来源任务 |
| --- | --- | --- | --- | --- |
| 重放一致性 | 同一事件流重放 100 次，状态 hash 相同 | 100/100 | — | A07 |
| 中断点恢复一致性 | 12 个不同中断点 kill 后恢复，终态与不中断一致 | 12/12 | — | A26 |
| 副作用重复次数 | 50 次随机重启实验中重复执行的副作用数 | 0 | — | A38 |
| 断点恢复成功率 | 恢复后成功跑到终态的比例 | ≥95%（≥48/50） | — | A38 |
| 越权拦截率 | 构造 20 次越权调用，被拦截比例 | 100% | — | A22 |
| 平均恢复耗时 | 从 kill 到继续执行的时间 | <5s | — | A38 |
| 工具调用成功率 | 成功执行且结果合法的调用 / 总调用次数 | ≥96% | — | A18 起累计 |

**讲述顺序建议**：先讲「副作用重复 0 次」（最反直觉、最容易记住），再讲「12/12 恢复一致」（最有说服力），最后讲「平均 3.x 秒恢复」（说明工程可用性）。

## 八、两处需要写进 README 的决策（排期表明确要求）

这两条排期表标注了「写进 README 也是加分项」，因为它们是**主动暴露设计约束**的证明：

1. **为什么不用原生 EventSource（A33）**：原生 `EventSource` 带不了自定义 header，JWT 鉴权无法通过；因此用 `fetch-event-source`，代价是要自己实现断线重连与 `Last-Event-ID` 续传。**这个代价是明码标价的，不是不知道。**

2. **为什么审批后前端必须重拉快照（A35）**：前端不能撒谎。审批结果以服务端为准，前端不做本地状态推断——否则网络异常时界面显示「已批准」，后端仍是 pending。**宁可多一次请求，也不让界面与后端不一致。**
