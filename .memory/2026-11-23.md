## 五轮定位讨论 → 产出 `docs/项目定位.md`

- **起因**：用户连续追问项目的求职价值，而不是要改代码。四问依次是（m00146 后 / m00361 / m00366）「这个任务完成了什么」「这个项目具体是干什么的」「是做什么业务的」、m00379「项目不往一个具体的业务方向做，在面试有优势吗」、m00387「做出来的项目不就等于工具吗」、m00393「现在大多数简历上都是写的系统项目，我们不做系统，是不是会显得我们做的只是半成品」。
- **讨论得出的六个结论**（都已写进 `docs/项目定位.md`）：
  1. 定位类比：本项目之于 Agent 应用 ≈ **WAL 之于业务系统**。是「正确性层」不是「编排层」。
  2. 回答「重写 LangGraph」：LangGraph 提供**编排**（下一步干什么），本项目提供**正确性**（干完能否被证明干过且只干一次）；LangGraph checkpoint 是序列化整个 state，状态结构一变历史 checkpoint 全废，且不解决副作用去重；Temporal 不懂 Agent 语义。
  3. 护城河是 A19 幂等键 + A20 两阶段标记 + A21 重启后三态判定，排期表原文标注 A21「本项目最硬的一处」。这三步讲不透，项目就掉成「重造轮子」。
  4. 业务是载体不是目的：A18 六个工具（查工单 / 建工单 / 发邮件模拟 / 查日志 / 只读 SQL / 发通知）构成「企业工单台 + 通知」场景，全换成电商或文件批处理内核一行不改。
  5. **措辞双轨**：对外（简历/HR）用「系统 / 控制台」，对内（README/技术面）用「内核 / 库」。README 要主动缩小范围再在范围内无可挑剔——写「Agent 执行系统」会招来「那你用户体系呢」。
  6. 「半成品」不由「是不是系统」定义，由**链路是否闭合**定义。P8 控制台（32h，占 15% 工时）让它形态上就是系统；真正的风险是砍任务时凭直觉砍掉 P9/P10（测试与文档），那才是致命的，因为价值全在「可验证」上。
